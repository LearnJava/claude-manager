# AI-STACK — как работать с ИИ в claude-manager и как его программировать

Сводный документ по итогам разбора ветки `master` (@ 62fef46) и подключения GLM.
Все номера строк относятся к master. Дата: 2026-11-06.

---

## Часть I. Модель мира: три слоя и две оси замены

```
┌──────────────────────────────────────────────────────┐
│  Менеджер (ядро, Go + GUI)                           │
│  очередь задач, worktree-слоты, crash-recovery,      │
│  деньги, логи, разрешения, UI                        │
├──────────────────────────────────────────────────────┤
│  Агент (Runtime): Claude Code │ Hermes │ ZCode       │  ОСЬ 1: замена «тела»
│  руки: сам выполняет Bash/файлы/todo                 │  через адаптер Runtime
├────────────────── Формат Anthropic ──────────────────┤
│  Мозг (модель): Claude … │ GLM                       │  ОСЬ 2: замена «мозга»
└──────────────────────────────────────────────────────┘  через совместимость API
```

Ключевые факты:

- **Модель никогда не работает сама.** Она лишь возвращает блоки `tool_use`
  («выполни такую-то команду»), а исполняет их агент — локально, со всеми
  механизмами (разрешения, todo, стрим логов). Работа с инструментами — часть
  протокола Anthropic (поле `tools` в запросе, `tool_result` в ответе).
- **«Формат Anthropic»** — сетевой протокол Messages API: `POST /v1/messages`,
  JSON-запросы/ответы с блоками контента, SSE-стриминг. Claude Code — родной
  клиент формата; `api.z.ai/api/anthropic` — фасад, который выучил формат и
  отвечает им, а внутри крутит GLM.
- **Смена мозга = ноль кода** (URL + ключ в настройках CLI).
  **Смена тела = адаптер** (`Runtime` + `Parser` + контрактные тесты).

Правило выбора пути при подключении новой ИИ (по возрастанию цены):

1. есть Anthropic-совместимый эндпоинт → **ноль кода**, правим только настройки;
2. есть OpenAI-совместимый → дешёвый мост, но нужен код;
3. свой CLI/протокол → полный адаптер Runtime (как Hermes/ZCode).

## Часть II. Как работать (эксплуатация)

### II.1. Подключение GLM как мозга Claude Code

Эккаунт Anthropic забанен — не помеха: после переключения запросы вообще не идут
на `api.anthropic.com`. Настройка — один раз, навсегда, файл
`C:\Users\konstantin\.claude\settings.json`:

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.z.ai/api/anthropic",
    "ANTHROPIC_AUTH_TOKEN": "<ключ GLM Coding Plan>",
    "API_TIMEOUT_MS": "3000000",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "glm-5.3-flash",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "glm-5.3",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "glm-5.3"
  }
}
```

Логика раскладки: Haiku в GUI — «дешёвый работник» (метки качества, судья,
мелочь) → флэш; Sonnet/Opus — основная работа → `glm-5.3`.

Модели (docs.z.ai/devpack/latest-model, все ярусы плана Max/Pro/Lite):

| id | что умеет |
|---|---|
| `glm-5.3` | только текст |
| `glm-5.3-flash` | **мультимодальная** — единственная, что понимает картинки |
| `glm-5.3[1m]`, `glm-5.3-flash[1m]` | контекст 1M; требует `"CLAUDE_CODE_AUTO_COMPACT_WINDOW": "1000000"`; если CLI говорит «модель не существует» — обновить Claude Code |

Проверка после настройки: `claude` → `/status` (откуда настройки, какая модель),
`/effort`. Перед этим убедиться, что в окружении пусто `ANTHROPIC_API_KEY`.

Несколько файлов настроек: у CLI есть флаг `--settings <файл>`, проектный
`.claude/settings.json` и `CLAUDE_CONFIG_DIR`, но менеджер на master их не
передаёт — внутри GUI работает один пользовательский settings.json. Он и не
нужен другой: смена модели в GUI меняет `--model`, а во что тот превратится,
решают `ANTHROPIC_DEFAULT_*` из этого же файла.

### II.2. Что выбирать в GUI менеджера

| Поле GUI | Что выбрать | Что происходит на самом деле |
|---|---|---|
| Рантайм/сессия | **claude** | агент — Claude Code, GLM за фасадом невидима |
| Модель | Haiku / Sonnet / Opus / Fable | `--model <алиас>` → CLI резолвит через `ANTHROPIC_DEFAULT_*` → на фасад уезжает GLM. Имена claude в GUI — маска; реальное потребление квот видно в кабинете z.ai |
| Effort | low / medium / high / xhigh / max | `--effort` → фасад мапит: low/minimal/light→low; medium/high→high; xhigh/max→ultra→max; не задано→**max** (дефолт). Отключить thinking нельзя совсем — off→low с лёгким thinking |

### II.3. Что делает ИИ за сессию (набор действий, кроме «после рана»)

**До старта:** preflight-анализ задачи с планом на одобрение; подбор модели;
проверка окружения.

**Старт:** запуск CLI с флагами (модель, режим разрешений, папка работы — корень
или слот worktree-пула); первый промпт по приоритету: crash-recovery → задача из
очереди → «задач нет, жди указаний» → свой промпт из конфига; затравка о
проекте (primer, опция).

**Работа (протокол агента, переносим на любого ИИ текстом):**
- взять задачу из файла очереди строго сверху вниз (порядок = зависимости);
- cm-task-start: `git pull`, ветка = бронь задачи; своя незаконченная ветка →
  **продолжить её**, не начинать заново; занять слот worktree, опубликовать ветку;
- работать: читать/править файлы, запускать команды; опасное — через очередь
  разрешений в GUI; развилки — вопросы в GUI (у автономных есть таймаут);
- todo-список виден в карточке сессии;
- cm-task-finish: гейты (тесты) один раз синхронно → красный = чинить, не
  подавлять → обновить доки/журнал → убрать указатель из очереди → merge --no-ff
  → push → освободить слот, удалить ветку.

**Менеджер следит:** живой лог; токены/деньги (ран/день/проект); контекст — на
пороге (~75%) дистиллирует саммари и открывает свежий процесс с ним (handoff);
ловит зацикливание; реагирует на сбои API (см. таблицу ниже); смена модели на
лету (интерактивный разговор не теряется — `--resume`); ограничители «стоп
после задачи» и MaxTasks.

**Реакции на исход рана (жёсткая таблица ядра, session.go ~1230–1340):**

| Что случилось | Реакция ядра |
|---|---|
| чистый конец | очистить state, взять следующую задачу |
| rate limit | пауза / fallback-модель, повтор |
| session not found | стереть state, новая беседа |
| auth error | стереть state, ротация UUID, пауза 60 с |
| context restart | свежий процесс с саммари (handoff) |
| другая ошибка | ротация UUID (анти-«id занят»), пауза, повтор |

### II.4. Crash recovery глазами пользователя

Сессия не теряется, потому что: (1) лаунчер `run-claude-manager.bat` возвращает
менеджер после краша (до 10 раз, отличая выход по кнопке — маркер
`state/clean-exit` — от падения); (2) на диске лежит `state/<проект>-<сессия>.json`
с id беседы, задачей и папкой — он переживает любую смерть процессов; (3) UI не
даёт молча ни потерять, ни затереть незаконченный ран.

Маркер ⏸ у сессии = файл с `session_id` существует, ран не закончен. Клик ▶ →
диалог **Продолжить / Начать заново / Отмена** (с задачей, временем старта, id
беседы). Файл стирается только при: чистом конце рана, session not found, auth
error, context restart, интерактивном ране без задач, или файле без `session_id`
(крах до первого init).

## Часть III. Как программировать (правила разработки)

### III.1. Существующий шов

`internal/session/runtime.go` — контракт, уже реализованный для двух бэкендов:

```go
type Runtime interface {
    Name() string                                  // "claude" | "hermes"
    PerTurnProcess() bool                          // процесс на ход (Hermes) или на задачу (Claude)
    Args(s *Session, autonomous bool, convID, imagePath string) []string
    NewParser() Parser
}
type Parser interface {
    Parse(line string) []ParsedEvent               // stdout → общий формат
    Flush() []ParsedEvent
    LastError() string
}
```

Выбор реализации — в одном месте (`newRuntime` в `New()`). Весь stdout любого
бэкенда нормализуется в `ParsedEvent`; `handleEvent`, менеджер и GUI работают с
ним одинаково. Инструкция добавления рантайма: `docs/runtimes.md` §7; контрактные
тесты: `runtime_contract_test.go` (§11a); различия, которые формат не скроет: §6.

### III.2. Заповеди (менять только по явному указанию владельца)

0. **Контракт неизменен.** Правила ниже и контракт действий (III.3) меняются
   только владельцем проекта. Механизм закрепления — не обещания, а код:
   контракт существует как исполняемые тесты; его изменение видно в diff.
1. **Ядро не знает имён рантаймов.** Никаких `if runtime == "claude"` вне папки
   адаптера. Ветвиться можно только на `PerTurnProcess()` (и то — это допуск,
   описанный в доке). Закрепить отдельным guard-тестом, который падает при
   появлении имени бэкенда в коде ядра.
2. **Новая ИИ = адаптер, не правка ядра.** Адаптер: транспорт/argv, парсер
   событий → `ParsedEvent`, capability-флаги, маппинг разрешений, метаданные
   для GUI (модели, effort, лейблы). Обязан пройти контрактные тесты.
3. **Сначала дешёвый путь.** Anthropic-совместимый фасад → OpenAI-мост → и
   только потом адаптер. Проверять наличие фасада до написания кода.
4. **Возможности объявляются, а не предполагаются.** У каждого бэкенда свой
   набор «умеет/не умеет» (Hermes без `--append-system-prompt`; ZCode со своими
   режимами разрешений). Ядро деградирует по capability-флагам, молчаливое
   «все умеют всё» запрещено.
5. **Идентичность результата = форма, не содержание.** Контракт гарантирует
   одинаковую форму отчётности (события, жизненный цикл, идентичность беседы),
   а не одинаковое качество работы разных моделей. Не пытаться гарантировать
   второе.

### III.3. Контракт действий (правила-гарантии для реализатора адаптера)

Каждое действие фиксируется наблюдаемой гарантией; реализатор сам подбирает
команды и аргументы:

| # | Действие | Обязательная гарантия | Реализатор выбирает сам |
|---|---|---|---|
| 1 | Начать ход | ровно один финальный `Result` на ход | argv, флаги, транспорт |
| 2 | Новая/продолжить беседу | непрозрачный id беседы; `resume(id)` продолжает ту же беседу | `--session-id`/`--resume`, conv-id, RPC |
| 3 | Отправить текст | текст доходит, порядок сохраняется | stdin-JSON, RPC |
| 4 | События хода | нормализованный набор: лог, tool-call, todos, usage, result, классификация неудачи | формат стрима, парсинг |
| 5 | Разрешения | запрещённое не выполняется молча — превращается в запрос с вариантами | режимы CLI, брокер |
| 6 | Вопрос пользователю | единый формат «вопрос + варианты», ответ доходит адресно | AskUser, clarify, RPC |
| 7 | Стоп/прерывание | мягкий завершает ход; жёсткий убивает всё порождённое без сирот | SIGINT, job kill, RPC-cancel |
| 8 | Смена модели на лету | следующий ход на новой модели, беседа не теряется | рестарт с resume, флаг, RPC |
| 9 | Токены/деньги | usage (in/out/cache) на каждый ход | из стрима, из API, расчётно |
| 10 | Сигнал контекста | если умеет — использование контекста; не умеет — обязан заявить | events, расчёт |

Честные границы (не абстрагируется): качество самих решений ИИ; уникальные фичи
CLI (только через capability-флаги); транспортная форма — текущий контракт
«локальный процесс с argv и построчным stdout», чистый HTTP-API потребует
расширения контракта (по указанию владельца).

### III.4. Логи

Три слоя, из них переносим только один:
- **живой стрим в GUI** — уже нормализован (`ParsedEvent`), рантайм-агностичен;
- **персистентность** (SQLite, retention `DeleteOldLogs`, md-лог рана, logship
  с маскировкой секретов) — целиком ядро, нового ИИ не касается;
- **входной формат стрима** — обязан переводить адаптер (это контракт №4).

Известная дыра ядра (не зависит от рантаймов): pending-логи живут в памяти и
сбрасываются на диск только в `finishRun` — рестарт менеджера теряет раны.

### III.5. Карта рантаймов

| ИИ | Формат Anthropic? | Цена подключения |
|---|---|---|
| Claude (api.anthropic.com) | да, родной | уже есть |
| GLM (api.z.ai/api/anthropic) | да, фасад | **ноль**: настройки CLI |
| Hermes | нет, свой стрим | адаптер (есть) |
| ZCode | нет, app-server | адаптер (slim-for-kimi) |

## Часть IV. Известные дефекты master (to-fix)

1. **Pre-launch save стирает `session_id`** (`session.go:1610`): перед каждым
   запуском CLI файл состояния перезаписывается целиком с пустым `SessionID`;
   крах в окне «запуск → init» теряет указатель на прерванную беседу —
   предлагается «начать заново». Комментарий там обещает обратное. Фикс —
   подставлять `SessionID: s.resumeSessionID` (или последний `CLISessionID`).
2. **После watchdog-рестарта сессии не поднимаются сами**: комментарии
   (`app.go:413`, `run-claude-manager.bat`) обещают «crash recovery resume the
   sessions», но авто-запуска нет — сессии стоят idle с ⏸ до ручного клика.
   Либо реализовать автоподъём, либо поправить комментарии.
3. Мелочи: `UpdateSessionID`/`UpdateWorkDir` — read-modify-write без контракта
   блокировки; `started_at` в ResumePrompt — время последней попытки, не старта
   беседы; устаревший комментарий у `ResumeSession` («full resume deferred» —
   через state-файл работает).

## Приложение: чек-лист подключения новой ИИ

1. Есть Anthropic-совместимый эндпоинт? → прописать env в settings.json, выбрать
   claude-рантайм, проверить `/status` и `/effort`. Готово.
2. Нет, но есть CLI: реализовать `Runtime` + `Parser` → `ParsedEvent`;
   объявить capability-флаги и маппинг разрешений; отдать метаданные GUI
   (модели/effort/лейблы); прогнать `runtime_contract_test.go` + свой набор;
   убедиться, что guard-тест «ядро не знает имён» зелёный.
3. Контракта не хватает (новый класс бэкенда)? → предложение владельцу, изменение
   контракта и тестов единым коммитом, все существующие адаптеры — прогон заново.
