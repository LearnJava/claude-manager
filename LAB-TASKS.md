   (`docs/Science_lab/measurements/2026-10-28-ab-pilot/`, клоны `cm-bench/a`, `b`, `_logs/`).
3. **Конфиг менеджера не трогать** (`.claude-manager/config*.toml`, `~/.claude-manager/`). Рекомендации по настройкам
   пишутся в документ.
4. **Каждое число с источником:** скрипт и команда, таблица БД или файл. Измеренное отделять от вывода. Догадку

   на них опираются (LAB-01, LAB-02), идут первыми.

## LAB-01: на что уходит запись в кэш: старт сессии или рост разговора

**Depends on:** —

**Files:** `docs/Science_lab/lab-tools/cache_write_split.py`, `docs/Science_lab/measurements/<дата>-cache-write/RESULTS.md`,
`docs/Science_lab/README.md`

**Зачем.** В пилоте запись в кэш дала 47% стоимости B ($4,05 из $8,64) и 30% у A ($1,33 из $4,40) (`ab-pilot-tools/cost.py`).
Не проверено, какая часть записи приходится на стартовый контекст сессии (системный промпт, CLAUDE.md, инструменты,
первые чтения), а какая на рост разговора (выводы команд, прочитанные файлы). От ответа зависит, что экономить:
число сессий или содержимое контекста.

**What to do.**
1. По транскриптам сессий пилота (A и B; как найти их, см. `ab-pilot-tools/cost.py` и `cm-bench/_kit/bench_measure.py`)
   взять `usage` каждого вызова модели: `cache_creation_input_tokens` с разбивкой
   `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`, `cache_read_input_tokens`, `output_tokens`.
2. Разделить запись на: (а) первый вызов сессии, (б) вызовы до первого `Edit`/`Write` (разведка), (в) остальное;
   и отдельно (г) повторную запись того, что уже было записано: кэш истёк или промпт сменился (признак: запись
   большого объёма посреди сессии после паузы дольше TTL).
3. Перевести в $ по `PRICES` и множителям записи 1,25× (5 мин) и 2× (1 ч); сверить сумму с `cost.py` (расхождение
   больше 2% объяснить).
4. Тот же разрез по всем сессиям claude-manager за последние 30 дней (`session_runs` + транскрипты по `cli_session_id`),
   медианы по ролям: разработчик, Chat, фоновые (аналитики, журнал).

**Done when:** `RESULTS.md` содержит таблицу A/B: $ и доли (а)–(г) с источником, сверку с `cost.py`; таблицу по ролям за
30 дней; вывод, что дешевле резать: число сессий, стартовый контекст или рост разговора, с отметкой «измерено» /
«вывод». Строка в `docs/Science_lab/README.md`. `go build ./...` и `go vet ./...` зелёные.

## LAB-02: расчётная модель «Opus с окном 1M против Sonnet с передачей на 150K» (H8, шаг 1)

**Depends on:** LAB-01 (тот же разбор `usage` по вызовам; переиспользовать его код)

**Files:** `docs/Science_lab/lab-tools/window_model.py`, `docs/Science_lab/measurements/<дата>-window-model/RESULTS.md`,
`docs/change-acceptance.md` (строка H8 в §6), `docs/Science_lab/README.md`

**Зачем.** Нужно правило: для какой задачи дешевле одна длинная сессия Opus 5.5 с окном 1M, а для какой Sonnet 5.5 с
передачей контекста (`context_handoff`, `handoff_context_tokens`) на ~150K. По таблице цен Claude API на 06.10.2026:
ввод Opus 5.5 $4 / Sonnet 5.5 $2, вывод $20 / $10, чтение кэша у обоих $0,20 за 1M токенов. Сверить с `PRICES`; если
там не так, считать по `PRICES` и отметить расхождение.

**What to do.**
1. По сессиям с передачей контекста (`app.log`: события handoff; `session_runs`) посчитать: число передач, токены
   итога передачи, **повторное открытие после передачи**: чтения файлов (`action_signatures`, `tool` = Read/Grep/Bash
   с `cat`/`sed`), уже сделанные до передачи в той же задаче (`task_ptr`), их токены (`result_chars`/`out_tokens`) и
   вызовы до первой записи после передачи.
2. По длинным сессиям без передачи: средний контекст на вызов как функция номера вызова (рост d токенов за вызов).
3. Модель стоимости задачи из N вызовов: 1M-вариант ≈ Σ контекст_i × цена чтения + запись нового + вывод;
   вариант с передачей: тот же расчёт с потолком контекста плюс стоимость повторного открытия на каждую передачу.
   Параметры брать из п. 1–2 (медианы), не придумывать.
4. Точка безубыточности: при каком отношении вызовов Opus/Sonnet и при какой длине задачи (N, пиковый контекст)
   варианты равны. Таблица и, если удобно, PNG-график в каталоге измерения.
5. Записать, чего модель не учитывает: другое число вызовов у Opus, качество на длинном контексте, брак на стыке
   передачи. Это проверяется только прогоном (шаг 2 H8, схема 2×2 «модель × окно» на большой задаче T6), его не делать.
6. В `docs/change-acceptance.md` §6 добавить строку **H8** «модель × окно для больших задач»: ожидание из модели,
   метрика «$ на принятую задачу», охрана «скрытые тесты не хуже, вмешательства 0».

**Done when:** `RESULTS.md` с измеренными параметрами (каждый с источником и n), формулой, точкой безубыточности и
списком неучтённого; строка H8 в §6; строка в README. Платных прогонов не было.
