(`PYTHONIOENCODING=utf-8 python -I window_model.py [--days 30] [--handoff-tokens 150000]`), переиспользует разбор
`usage` из `cache_write_split.py` (LAB-01; в словарь вызова добавлены поля `ot`, `mdl`). Полный вывод — `tables.md`,

Цены, множители: `PRICES`, `W5=1.25`, `W1H=2.0`, `READ=0.10` из `claude-code-setup/tools/measure/cost_attribution.py`.
Чтение кэша = `READ` × цена ввода.

**$0,40 у Opus 5.5** (ввод $4). Считал по `PRICES`; вариант «Opus $0,20» дан как чувствительность. Таблицу цен API

## 3. Модель

Задача из N «продуктивных» вызовов. Вызов i: чтение контекста × цена чтения + прирост × цена ввода × множитель записи
(1h, 2,0) + вывод × цена вывода; первый вызов пишет контекст старта 30,6K. Opus: потолка нет. Sonnet с передачей: когда
контекст перешёл бы 150K — вызов с чтением контекста и итогом 519 токенов вывода, новая сессия со стартом 30,6K+519,
затем накладные (E вызовов, R токенов). Функции `session_cost` и `break_even_ratio` в скрипте.

Основной вариант (медианы, `PRICES × READ`, накладные — верхняя граница), $ за задачу:

| N вызовов | Sonnet без потолка | Sonnet + передача (число передач) | Opus 1M (пик контекста) | Opus / Sonnet+передача при равных вызовах | Точка безубыточности: вызовов Opus / вызовов Sonnet |
|---|---|---|---|---|---|
| 25 | 0,52 | 0,52 (0) | 1,05 (57K) | 2,00 | 0,38 |
| 50 | 1,06 | 1,06 (0) | 2,11 (84K) | 2,00 | 0,51 |
| 100 | 2,53 | 2,53 (0) | 5,06 (138K) | 2,00 | 0,58 |
| 150 | 4,54 | 4,20 (1) | 9,07 (192K) | 2,16 | 0,58 |
| 200 | 7,08 | 5,75 (1) | 14,16 (245K) | 2,46 | 0,55 |
| 300 | 13,78 | 9,32 (3) | 27,57 (353K) | 2,96 | 0,51 |
| 500 | 33,63 | 15,51 (5) | 67,26 (568K) | 4,34 | 0,42 |
| 800 | 79,51 | 24,90 (8) | 159,02 (890K) | 6,39 | 0,35 |

Чувствительность (полные таблицы — `tables.md`): накладные передачи 0 — безубыточность на N=300 0,45, на N=800 0,32;
средний прирост вместо медианы — 0,57 / 0,45 / 0,31 на N=100 / 300 / 800 (при среднем приросте пик Opus на N=800 — 1558K, то есть окно 1M переполнено и модель Opus там неприменима); чтение Opus
$0,20/М — безубыточность поднимается до 0,70–0,79 на N=100–300 и 0,49 на N=800.

Что показывает модель (вывод из расчёта, не измерение):

- При равном числе вызовов Opus дороже вдвое уже на коротких задачах: цена ввода и вывода вдвое выше, и это не зависит
  от окна. Передача на 150K добавляет Sonnet ещё преимущества на длинных задачах (контекст не растёт выше 150K, у Opus
  чтение на пике дороже в разы).
- Чтобы Opus окупился, ему нужно решить задачу **примерно за 40–60% вызовов Sonnet** (0,35–0,58 в таблице; 0,7–0,8 при
  чтении $0,20/М). Окно 1M само по себе выигрыша не даёт: передача Sonnet стоит 4,2–15 $ против 9–67 $ на 150–500 вызовах.
- Выигрыш Opus мог бы быть только в числе вызовов (меньше блужданий) и в браке на стыке передачи — оба эффекта в расчёт
  не входят.

## 4. Что модель не учитывает

- **Число вызовов у Opus.** Единственный свободный параметр r; проверяется только прогоном (шаг 2 H8, схема 2×2
  «модель × окно» на большой задаче T6) — не запускалось.
- Качество на длинном контексте у обеих моделей и брак на стыке передачи (потеря деталей в итоге на 519 токенов).
- Накладные передачи оценены границами 0 и 19K токенов, n=5 передач, из них вызовы до первой записи только у 3.
- Профиль токенов постоянен (линейный рост); реальный контекст при автосжатии и субагентах ведёт себя иначе.
  Транскрипты показывают рост без сжатия, частота сжатия не измерялась.
- Кэш TTL, паузы ожидания и повторная запись после простоя (корзина d в LAB-01 — 1–8% записи) не моделируются.
- Время: Opus дольше или быстрее на вызов — не измерялось.
- Допущения: 4 символа на токен для итога передачи; 100% записей 1h (так записан usage; проверить: `cache_write_split.py`).
